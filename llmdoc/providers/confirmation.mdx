# 模型绑定与启动确认 / Model Binding and Launch Confirmation

Provider 的 key、base URL 和 model 是一个完整绑定。profile ID 是 owner 范围内的配置引用，既不是凭据，也不等于已冻结的运行配置。限速、并发、结构化输出和原生搜索声明属于该绑定的运行策略；更换 provider 时不能顺带继承原 provider 的策略。

Provider key, base URL, and model form one complete binding. A profile ID is an owner-scoped configuration reference, neither a credential nor a frozen run configuration. Rate limits, concurrency, structured-output behavior, and native-search declarations belong to that binding; a replacement provider cannot inherit the old provider's policy accidentally.

## 配置选择与权限 / Configuration Choice and Authority

已保存的 profile 由后端按当前 owner 读取，客户端只获得显示信息、密钥是否存在及不透明的 `confirmation_token`。该令牌检测用户查看配置后发生的漂移，不代替 signed principal 或资源授权。profile 密钥保留在本地 SQLite；临时 BYOK 的 key 等凭据只随当前请求在内存中传递，不写入 Scenario、replay、snapshot 或日志。非敏感的模型、base URL 或限速元数据可按各运行合同保存，不能把它们与凭据混为一类。

远端显式覆盖必须提供完整 key、URL、model；精确本地端点可使用完整的免 key URL、model 绑定。只改模型、地址或 key 的部分覆盖不能偷偷借用旧 profile 的凭据。完整 provider 更换会解除旧 profile 归属，只有请求明确提供的运行限制随新绑定生效。

Saved profiles are resolved by the backend for the current owner. The client receives display data, whether a key exists, and an opaque `confirmation_token`. That token detects configuration drift after review; it does not replace the signed principal or resource authorization. Profile keys remain in local SQLite, while temporary BYOK credentials live only for the current request and never enter Scenario, replay, snapshot, or logs. Non-secret model, base-URL, or rate-limit metadata may be saved by the applicable run contract. A remote explicit override must provide key, URL, and model together; an exact local endpoint may use a complete keyless URL-and-model binding. Partial overrides cannot borrow an old profile's credentials. A complete provider replacement drops the old profile association and carries forward only explicitly supplied run limits.

## 确认与后台任务 / Confirmation and Background Work

首页把实际问题、规模、provider、reasoning effort 和搜索选项一起保存为待确认请求。使用 profile 时同时保存当时的令牌；缺少令牌不得假定配置可确认。身份预检、单次创建和多次运行创建都验证传入令牌，配置变化返回 `MODEL_PROFILE_CHANGED`，在模型调用、Scenario 插入和任务安排之前停止。刷新只更新可供核对的配置，用户须重新确认后启动。

令牌校验与 provider 解析针对同一份持有的 profile 对象。已接受的确认请求以不可变 `ResolvedProviderPolicy` 贯穿解析、worker 交接和模拟器，不能在下一阶段重新读取同名 profile。显式空值和 false 也属于已确认策略，不得被后续编辑或旧上下文补回。该保证只适用于实际校验并传递确认信息的入口；不能因为一个请求带 profile ID 就推定它有相同保证。

已接受运行还要把 effective reasoning effort 绑定到 run scope。角色准备、叙事、分支、结论、流能力探针和 fallback 都消费这一 scope，不能在辅助阶段改成另一强度。Debate 把同一选择保存到 run config；Scenario 后续的报告、Ending Room、Survey 和 Analyst 在各自重新解析 provider 时继承已保存的运行 effort，除非该操作提供新的显式选择。

The homepage stores the actual question, scale, provider, reasoning effort, and search choices as a pending confirmed request. A profile-backed request also stores the reviewed token; missing tokens are never assumed valid. Identity preflight, single creation, and multi-run creation validate the token before model calls, Scenario insertion, or scheduling. Drift returns `MODEL_PROFILE_CHANGED`; refresh only updates what can be reviewed, so launch still requires reconfirmation. Token validation and provider resolution use the same held profile object. An accepted request carries an immutable `ResolvedProviderPolicy` through parsing, worker handoff, and simulation without re-reading a same-named profile. Explicit null and false values are part of the policy. The guarantee applies only to entry points that actually validate and transmit confirmation. The accepted run also binds its effective reasoning effort to run scope. Role preparation, narration, branching, conclusions, streaming probes, and fallbacks consume that scope. Debate stores the choice in run config; later Scenario reports, Ending Room, Survey, and Analyst inherit the saved run effort when they re-resolve a provider unless the operation explicitly chooses another effort.

## 后续操作与继承 / Follow-Up Operations and Inheritance

后续报告、分析、圆桌和恢复操作按本次操作重新解析已保存的 profile 指针，或采用本次完整显式 provider；它们不自动沿用新建运行曾持有的不可变 provider 对象。读取历史模型标签不证明今天仍能恢复该绑定；缺失或跨 owner 的 profile 不应静默替换成服务端模型。完整显式 BYOK 可以解除继承，但不能把新的 endpoint 与旧 key 拼接。

历史索引优先显示当时保存的模型描述。只能从当前 profile 回查到的信息标为 `current_profile`，不能把后来编辑的名称或模型声称为旧运行实际使用的绑定。

圆桌、分析与辩论还有自己的操作 scope 和重启规则，分别由对应 owner 文档约束。前端在异步期间切换用户、对象、分支、profile 或语言时，旧请求的返回值不得作为新 scope 的模型状态、导出内容或保存依据。

Later reports, analysis, roundtables, and recovery operations re-resolve the saved profile pointer for that operation or accept a complete explicit provider; they do not retain the immutable provider object from initial creation. A historical label does not prove that the binding is recoverable today. A missing or cross-owner profile cannot silently become the server model. Complete explicit BYOK may override inheritance, but cannot combine a new endpoint with an old key. History prefers the model description saved at execution time. Information recovered only from a current profile is labeled `current_profile` and cannot rewrite historical attribution. Roundtable, analysis, and Debate keep their own operation scopes and restart rules. If the frontend changes user, object, branch, profile, or language during asynchronous work, an old response cannot become model state, exported content, or save input for the new scope.

## 能力与运行结果 / Capability and Runtime Outcome

RPM、TPM、并发、pending 和 purpose lane 是不同限制；空值继承、零值禁用及 reasoning effort 的精确优先级由配置与 LLM client 负责。Scenario 对会话模型的 readiness 必须在该 Scenario、owner 和 provider scope 内解析；全局 health、模型目录或 HTTP 200 不能替代它。上游正文、合法输出及流终态完成才构成成功；错误与取消必须保留明确失败语义，不能用本地回退冒充上游能力。

RPM, TPM, concurrency, pending capacity, and purpose lanes are separate limits. Configuration and the LLM client own null inheritance, zero-as-disabled behavior, and exact reasoning-effort precedence. Conversation readiness is resolved inside the specific Scenario, owner, and provider scope; global health, a model directory, or HTTP 200 cannot substitute for it. Success requires upstream body content, valid output, and a completed streaming terminal. Errors and cancellation retain explicit failure semantics, and a local fallback cannot impersonate upstream capability.
